# Architecture

A map of how the ~20k lines in `src/` fit together. This covers module responsibilities, ownership, threading, and control flow - not configuration (see [CONFIGURATION.md](CONFIGURATION.md)) or the build (see [BUILDING.md](BUILDING.md)).

Line numbers are call-outs to orient you, not guarantees - they will drift as the code changes.

## One binary, one owner of the config

`build.zig` builds one executable, `eve-maj-preview.exe` (entry point `main.zig`): the thumbnail/hotkey/notification app, which also hosts the configuration window in-process (see [The configuration window](#the-configuration-window-dialog)). `zig build config` runs it with `--config`, which opens that window, or asks an already-running instance to via the `OpenConfig` protocol command.

There is one in-memory model and one writer: `main.zig` owns the running profile (`g_store`, a `ProfileStore`) and the global settings (`g_global_settings`), and the configuration window edits those directly rather than its own copies on disk.

## Startup (`main.zig`)

`main()` → `mainImpl()` does, in order:

1. Install crash handling (`crash.zig`): vectored exception handler, unhandled exception filter and minidump support; `main.zig` keeps only the root `panic` declaration pointing at `crash.handlePanic`, which writes to `eve-maj.log`.
2. Check for `--protocol <url>` **before** the single-instance check, so protocol commands work even when another instance is already running; `protocol.forwardToRunningInstance` hands it over - see [protocol.zig](#protocolzig-and-cross-process-control).
3. Acquire a named mutex (`Global\EVE-Maj-Preview-SingleInstance`) to enforce single instance.
4. Load `GlobalConfig`, then the per-profile `Config` (default or `--profile`/`-p`).
5. Auto-register the `evemajpreview://` protocol handler if configured (`protocol.ensureRegistered`).
6. Construct subsystems in dependency order: `Scout` → `Painter` → `ChatlogMonitor` → the activity trackers (`activity/runtime.zig`'s `Trackers.setup`, which wires them into the monitor) → **then** start the chatlog worker thread, only once the trackers exist for it to feed. `reloadWithProfile` follows the same order, so a kept monitor's worker stays paused until the new trackers are wired in.
7. Register the hidden timer window (`WndProc` = `timerWindowProc`), `TrayIcon`, and a detached background thread for `UpdateChecker`.
8. Initial window scan and thumbnail creation, `HotkeyManager` setup, `SetTimer` at `config.timer.scanIntervalMs`.
9. Enter the classic `GetMessageA`/`TranslateMessage`/`DispatchMessageA` loop.

`timerWindowProc` is the app's central message dispatcher: tray clicks, `WM_TIMER` (→ `onTimerTick`, see below), `WM_HOTKEY`, profile switches, incoming `WM_COPYDATA` from a second CLI invocation, and the configuration window's calls (`WM_DIALOG_RPC`) and moves (`WM_DIALOG_MOVED`).

## The central state owner: `Painter`, not `state.zig`

Despite the name, `state.zig` is not an app-state struct - it's ~70 lines defining two enums (`VisibilityState`, `ThumbnailState`) plus the legal-transition helpers (`transitionVisibility`/`tryTransitionVisibility`) that enforce them for `VisibilityState`; `ThumbnailState` is a plain style-lookup key with no transition logic of its own (see `ThumbnailWindow.effectiveRenderState` below). Code that acts on EVE's own client windows (not thumbnails) lives in `clients/`: `actions.zig` has the stateless actions (`minimizeAllClients`, `closeAllClients`, `moveAllClientsToSavedPositions`, `moveClientToPosition`), `auto_minimize.zig`'s `AutoMinimizer` minimizes idle clients (tracking each monitor's last-focused client so one can be spared), and `auto_move.zig`'s `AutoMoveVerifier` moves clients to saved window positions and re-checks them while EVE may still be repositioning its window. Painter holds one of each and calls them from `update()`.

The actual central mutable-state owner is **`Painter`** (`painter.zig`, ~1800 lines): the thumbnail manager. It owns the set of `ThumbnailWindow`s and their state, keeps them in sync with what Scout finds, and schedules layout and redraws, delegating the work itself to the modules below. It owns:

- The thumbnail collection: `thumbnails: ArrayList(ThumbnailWindow)` plus HWND→index hashmaps for O(1) lookup.
- The full thumbnail lifecycle: `createThumbnail`, `destroyThumbnailResources`, `cleanupClosedThumbnails`. New thumbnails come from one path, `addMissingThumbnails`: per tick for newly found windows, and via `populate` at startup and after a profile reload. The options differ only where intended: auto-move follows `moveOnStartup` at startup, `autoMovePosition.enabled` for later arrivals, and never on reload, while a reload seeds system names from a `SystemNameSnapshot`. Every path reflows under one rule (`hasCountDependentLayout`), since `createThumbnail` sizes each cell against the count so far.
- Per-tick reconciliation of scan results into thumbnail state: `update()`.
- Notifications, including triggering TTS: `notify` (one client), `notifyAll` (every client, for global user actions), `updateNotifications`. Whether a notification feeds the "cycle to recently notified" queue follows from its type (`notification.isUserAction`), not the caller. Both take a `notifications/notification.zig` `Notification` payload (type plus optional `state`/`source`/`target`), and Painter turns it into display text in one place, `renderText` (currently `notification.defaultText`). Speech and sound for a shown notification go through `notifications/alert_effects.zig`, so Painter never touches `tts`/`sound` directly. The chatlog worker thread queues the payload, not text, so rendering happens on the main thread. Each thumbnail's on-screen notifications live in a `notifications/stack.zig` `NotificationStack` (newest first, bump-to-top per type, plus per-type throttle timestamps); the cycle-to-notified hotkey reads Painter's `notifications/notified_queue.zig` `NotifiedQueue`.
- Nothing for Travel Mode itself: left-behind detection is `travel/left_behind.zig`'s `check(painter, now)`, called on a throttled ~2s cadence from `onTimerTick`. Each thumbnail carries a travel-owned `ThumbnailState` (`travel`); Painter only calls `recordJump()` on it when a jump lands, and `check` reads it and raises alerts via `notify`. Compares each `ThumbnailWindow.system_name` (not jump-timestamp order) to find the group's current system, so a straggler who catches up is never mistakenly flagged just because their jump landed last - see [CONFIGURATION.md](CONFIGURATION.md#travel-mode).
- Deciding when to redraw: `renderThumbnail` diffs the thumbnail's cached `RenderSettings` to skip redundant redraws, then hands off to `thumbnail/overlay.zig` (see below).
- Applying layout to windows (`repositionAllThumbnails`, `resizeThumbnailIfNeeded`, `saveThumbnailPosition`). The math lives in `layout/`: `placement.zig` has the RegionFit/not-logged-in grid math plus a `Layout` view (config + thumbnail list, via `Painter.layout()`) for size, position and display-order queries; `monitors.zig` has monitor bounds and DPI lookups.
- DPS/mining/bounty/resource values feeding into the overlay.
- Transient overlays: a `drag/overlays.zig` `GhostOverlay` (field `ghost_overlay`) outlining other saved positions while dragging, and a `platform/gdi_overlay.zig` `HintBox` (field `hint_box`) - a generic centered two-line box that dragging (`drag/overlays.zig`'s `showDragHint`) and region select (`startRegionSelect`) fill with their own text. Fonts for both come from `FontCache.characterNameFont`.

Feature state that lives on each `ThumbnailWindow` is owned by its feature's module, not Painter: `render_cache` (`thumbnail/overlay.zig`), `notifications` (`notifications/stack.zig`), `auto_minimize` (`clients/auto_minimize.zig`, refreshed by `AutoMinimizer.check` itself), and `travel` (`travel/left_behind.zig`).

Each tracked character is a `ThumbnailWindow`: `hwnd`/`text_hwnd`/`thumbnail_id`, `source_hwnd`, cached display strings/colors, `visibility_state`, and the `render_cache` (`thumbnail/overlay.zig`'s `RenderCache`) used for render skipping. Its render state (Active/Inactive/Alert/Minimized/Dragging) isn't stored - `effectiveRenderState()` derives it live on each render from focus (`Painter.active_source_hwnd`), `isWindowIconic`, active notifications, and drag state. In `ClientList`/`Nothing` view modes, `hwnd`/`text_hwnd` are sentinel values rather than real windows - see [list_view.zig](#other-subsystems).

## Window discovery → rendering pipeline

**`clients/scout.zig`**'s `Scout` owns discovery. `scanForEveWindows()` drives `EnumWindows`, matching each window against `config.windowFilters` by class name first (cheap pre-filter), then by executable path, which is checked once per process and cached by PID; `findMatchingFilter` is the one matcher used for both new windows and re-checking tracked ones after a config reload. `trinityWindow`-class windows get a character name parsed from the title; other filters use their configured `name`. Three `SetWinEventHook`s (`EVENT_OBJECT_NAMECHANGE`/`CREATE`/`DESTROY`) catch window lifecycle events between polls; `Scout.update()` reconciles these with the periodic full rescan.

Rendering is split four ways:

- **`platform/win32.zig`** - Win32 constants, `extern` declarations (including the `DwmRegisterThumbnail`/`DwmUpdateThumbnailProperties` family), struct layouts, plus small helpers built directly on those bindings with no app-specific knowledge (window title/class/exe-path lookups, window identity checks like `isOwnProcessWindow`/`isExplorerOwned`/`isDesktopShellWindow`, `setClickThroughStyle`, `shellOpen`, the COM `showFolderPicker`). No EVE- or config-aware logic.
- **`painter.zig`** - the DWM integration and orchestration (above). `createThumbnail()` creates a borderless layered popup window, calls `DwmRegisterThumbnail` to bind the EVE client's live DWM thumbnail into it, then creates a *second* layered window stacked on top for GDI-drawn overlay content (border, text, notifications). Each visible thumbnail is therefore two HWNDs, not one.
- **`thumbnail/`** - the overlay drawn into that second window. `overlay.zig` builds `RenderSettings` from config and thumbnail state (`createRenderSettings`), compares them for the redraw skip, and paints them (`renderThumbnailOverlay`); `draw.zig` holds the pixel/text primitives it and Painter's drag hint/ghost overlays share (`drawBorder`, `drawExclusionOverlay`, `measureText`, `renderText`, ...); `font_cache.zig`'s `FontCache` (owned by Painter, passed in) caches GDI fonts per (slot, DPI).
- **`platform/gdi_overlay.zig`** - the shared GDI leaf module: `OverlayBitmap` (a top-down DIBSection selected into a memory DC), alpha-fixup helpers for GDI text output, pixel-buffer `fillRect`, buffer-truncating `toBufZ`/`measureTextWidth`/`truncateTextToFit`, `registerWindowClass` (the common `WNDCLASSEXA` registration boilerplate), plus `HintBox`, the generic centered two-line hint window. It depends on nothing app-specific. Used by `painter.zig`, `list_view.zig`, `notifications/history_panel.zig`, `main.zig`, and `region_select.zig`.
- **`platform/fonts.zig`** - embeds the bundled Cascadia Code/Mono TTFs and registers them process-privately (`AddFontMemResourceEx`) at startup, so GDI font lookups work on installs without Cascadia.

## Log monitoring and activity tracking

**`chatlog.zig`**'s `ChatlogMonitor` matches the threading model documented in [CONFIGURATION.md](CONFIGURATION.md#chatlog-monitoring): when `useThreading` is enabled (default), a dedicated worker thread owns all file I/O (`workerThreadMain` → `processCommands`/`pollLogFiles`/`checkNewLogFiles`), decoupled from the main thread by three mutex-guarded `EventQueue(T)` instances - `command_queue` (main → worker), `result_queue` and `notification_queue` (worker → main). The main-thread side of `ChatlogMonitor.update()` only pushes add/remove-character commands and drains the two result queues - explicitly the only point where worker-thread output touches `Painter`/`Scout`. With threading disabled, `update()` instead polls synchronously inline on the main thread under a small time budget. Which gamelog lines become notifications is decided by `notifications/gamelog_events.zig`'s `classify()`, a pure line → `Notification` mapping called from the worker.

**`activity/tracker.zig`** is the DPS/mining-rate math, fed by log lines parsed on the chatlog worker thread. `CombatWindow`/`MiningWindow` are fixed-capacity ring buffers (no heap allocation after init) computing trailing-window sums and per-bucket spark-chart data. Both trackers are explicitly cross-thread: the chatlog worker calls `addEntry`/`removeCharacter` while the main thread calls `refreshAll`/`getDps`/`getRate`, serialized by each tracker's own mutex.

**`activity/resources.zig`**'s `ResourceTracker` is unrelated to the chatlog pipeline above - it samples per-process CPU%/RAM/VRAM directly from the OS (`GetProcessTimes`, `GetProcessMemoryInfo`, and a PDH "GPU Process Memory" query for VRAM), keyed by `scout.EveWindow.process_id`. Main-thread only, no locking: `Trackers.tick` calls `sampleAll` on its own throttled interval (`config.resources.update_interval_ms`) and pushes the result into `Painter.updateResourceStatsForCharacter`, the same push-then-`renderDirtyThumbnails(null)` shape combat/mining/bounty use, just without their cross-thread queue.

**`activity/runtime.zig`**'s `Trackers` owns the live tracker instances for the current profile: `setup` creates the ones the config enables and wires them into the chatlog monitor, `releaseForReload` frees them once the worker is stopped (the resource tracker survives while still enabled), and `tick` pushes each tracker's values into Painter at its configured interval. See [CONFIGURATION.md](CONFIGURATION.md#resource-usage-overlay).

## Input & control surfaces

- **`hotkeys/`** - global hotkeys, split by concern:
  - `manager.zig` - `HotkeyManager` owns a single `hotkey_map: AutoHashMap(c_int, HotkeyAction)`, registration, suspend/dialog-pause, and `runAction()`, the one switch on the `HotkeyAction` union, which delegates to the modules below. Hotkey presses reach it through `handleHotkeyPress()`, which first gates on suspend/focus-requirement state; protocol URLs and the tray menu reach it ungated through `runGlobalAction()`.
  - `bindings.zig` - `HotkeyAction`, the ID bands (cycle-groups, global actions, per-character, profile-switch, app, URL) that let a single `WM_HOTKEY` ID reverse-map to an action (a global action's ID is the band base plus its `HotkeyAction` tag), and `global_bindings`, the table of single-key global actions (config field, description, matching `protocol.HotkeyAction`) that registration iterates and protocol requests are mapped through.
  - `cycling.zig` - every cycle (group, per-character, excluded, notified, all-clients, not-logged-in), all walking indices via one `CycleOrder` iterator, plus `CycleState`, the cursors not kept in config or `hotkey_map`, and the focus sync that moves them onto a manually focused client.
  - `membership.zig` - `Exclusions` (per-group exclusion lists plus the manual fallback for characters in no group), the exclusion toggle shared by shift-click and the ToggleExclusion hotkey, and the assign-hovered-thumbnail-to-group action.
  - `profile_switch.zig` - next/previous/specific profile hotkeys, handed to the main window as an async `WM_SWITCH_PROFILE`.
  - `launch.zig` - app, URL and return-to-last-app hotkeys.
  - `hook_bindings.zig` - `HookBindings`, the combo → hotkey-ID map, hook install/uninstall and "exact combo, else bare key" `WM_HOTKEY` dispatch that both low-level hooks share.
  - `keyboard_hook.zig`, `mouse_hook.zig` and `paste_upload.zig`, below.
- **`hotkeys/keyboard_hook.zig`** - a `WH_KEYBOARD_LL` hook matching keyboard chords (including bare-modifier triggers like plain "Shift", which a keyboard-API-based approach can't represent) against bound combos and re-posting matches as synthetic `WM_HOTKEY` messages; also swallows a hotkey's key-up after a successful action changes focus (unconditionally for the Win key, since Windows treats an unmatched key-up as a Start Menu press regardless of focus) so the newly-focused window doesn't see a phantom key-up. `armWinKeyCapture()`/`disarmWinKeyCapture()` additionally keep the hook alive and swallow Win down/up unconditionally while the config dialog is recording a new binding (which otherwise unregisters everything), reporting the capture to the dialog since a swallowed key never reaches its own DOM listeners.
- **`hotkeys/mouse_hook.zig`** - a `WH_MOUSE_LL` hook mapping mouse-button chords to hotkey IDs and re-posting them as synthetic `WM_HOTKEY` messages, mirroring `keyboard_hook.zig`'s shape so `HotkeyManager` doesn't need a separate input path for mouse buttons.
- **`input.zig`** - the thumbnail/text-window `WndProc`s, which share one handler for the messages both windows treat alike: left-click routing (plain clicks to `clients/activation.zig`, shift-clicks to `hotkeys/membership.zig`'s exclusion toggle, on mouse-down or mouse-up per `clickTrigger`), the hover cursor, and right-button drags, handed to `drag/thumbnail.zig` (single-thumbnail drag with snapping, or a Ctrl group move batched through `DeferWindowPos`). Snapping itself (screen edges, other thumbnails, ghost positions) is `drag/snapping.zig`'s `applySnapping`, shared with `drag/panel.zig`, whose `panelHeaderHitTest`/`beginPanelDrag`/`updatePanelDragRect` drive the list view's and History Panel's header drags.
- **`clients/activation.zig`** - `activate()`, where every thumbnail click, cycle hotkey and protocol switch ends: restore (optionally with the minimize animation suppressed), foreground, reconcile thumbnail states, dismiss click-suppressible notifications, and sync hotkey cycle positions.
- **`platform/focus_grant.zig`** - the "focus grant" workaround for `SetForegroundWindow` silently refusing to switch focus unless the caller "just received user input" (true for a real click on our own window, not for a hotkey-triggered or auto-minimize-triggered refocus): a permanently-registered, physically unreachable `RegisterHotKey` binding (unused vk, every modifier combo) stays alive purely to borrow its foreground-lock exemption on demand - `forceSetForegroundWindow()` injects a synthetic keypress matching that binding, and the resulting genuine `WM_HOTKEY` (handled first in `timerWindowProc` via `handleWmHotkey()`, ahead of `HotkeyManager`'s dispatch) does the actual `SetForegroundWindow` call.
- **`protocol.zig` and cross-process control** - parses `evemajpreview://action/params` URLs, handles registry registration/unregistration, and implements the IPC transport a second invocation uses to reach the running instance (`sendCommandToInstance`, which sends every `WM_COPYDATA` command through one `sendCopyData`, the receiving `copyDataBytes`, and `findExistingInstance`): character and profile switches, global hotkey actions, and `--config`'s `OpenConfig`.

**Call chain, hotkey press → character switch:**
`WM_HOTKEY` → `timerWindowProc` → `HotkeyManager.handleHotkeyPress` → an action handler (`cycling.zig`'s `cycleGroup`, `activatePerCharacterGroup`, `cycleExcluded`, `cycleNotified`, ...) → `Scout.getHwndByName` → `activation.activate` → `focus_grant.forceSetForegroundWindow`.

**Call chain, protocol URL → character switch:**
second process invocation with `--protocol "evemajpreview://switch/Name"` → `protocol.parseUrl` + `findExistingInstance` + `sendCommandToInstance` → running instance's `timerWindowProc` receives `WM_COPYDATA` → `Scout.getHwndByName` → `activation.activate` (same tail as above).

## `config.zig`

Not just JSON schema - it's the shared model layer with both a wire format and runtime logic. `config.zig` holds `Config` itself (wire hooks, validation, per-character lookups, the runtime save calls) and re-exports everything else, so callers only ever import `config.zig`. The sections live in `src/config/`:

- `thumbnail.zig`, `display.zig`, `behavior.zig` (timer, snapping, interaction, auto-minimize, auto-move, exclusion, close-all), `activity.zig` (combat/mining/bounty/resources overlays, travel), `notifications.zig`, `chatlog.zig`, `characters.zig`, `system_colors.zig`, `hotkeys.zig` (single-key actions and cycling groups), `window_filters.zig` - one file per settings area.
- `global.zig` - `GlobalConfig` and the cross-profile hotkey bindings and ore price table it owns.
- Every type that holds saved settings is named `XxxConfig` (`ThumbnailConfig`, `SystemColorConfig`, `HotkeyGroupConfig`, `GlobalConfig`, ...); plain values (`Position`, `Argb`, `VkCode`, `OreEntry`) aren't.
- `files.zig` - the process-wide `std.Io`/environment handles (`setIo`, `setEnvironMap`), file names and size limit, `atomicWriteFile`, `%VAR%` expansion.
- `profiles.zig` - profile files on disk: `profilePath`, `listProfiles`, `loadProfile` (creating the profiles folder and default profile, falling back to the default profile or to defaults), `saveProfile`, `writeDefaultProfile`.
- `chatlog.zig`'s `ChatlogConfig.fromWire` also fills empty log folders with EVE's defaults under the shell's Documents folder.
- `auto_colors.zig` - `AutoColorStore`, owned by Painter rather than `Config`: resolves system/character name and border colours (overrides first, then the unique generated colour), kept in `colors.json` rather than the profile and loaded on first use.

What the layer does:

- Each settings section (`ThumbnailConfig`, `DisplayConfig`, `CharacterConfig`, ...) is declared once as its runtime struct; a section only declares `pub const Wire = wire.Wire(Self)`, and `config/wire.zig` generates that JSON shape plus saving, loading, freeing and live-preview patching from its fields. `wire.encode`/`decode`/`free` (and the `*List` variants) work on any config type, using a type's own `toWire`/`fromWire`/`deinit` where it declares one (e.g. `ChatlogConfig`'s env-var expansion). Naming conventions pick the on-disk encoding: a `u32` named `*Color` is saved as a hex colour string, one named `hotkey*`/`*Key` as a hex key code; `std.ArrayList` fields are saved as arrays, a string map as an object, and fields named in `runtime_fields` (allocators, GlobalConfig's mutex, Config's profile name) aren't saved. A default a runtime field can't hold, like `Config.windowFilters`' EVE filter, goes in `wire_defaults`. `Config` and `GlobalConfig` are generated the same way; `Config.fromWire` adds only the DPI migration and resetting the `app`/`formatVersion` stamp, and `fromWire(.{})` is the default profile. `wire.toJsonAlloc`/`logJson` serialize and log either one the same way.
- Two independent settings layers: `GlobalConfig` (`profiles/global.settings.json` - last-used profile, cross-profile hotkeys, log level) and per-profile `Config` (`profiles/<name>.json`).
- `Config` itself is plain data with read-only helpers: per-character overrides (`getCharacterSize`, `isExcludedFromMinimize`, ...), `validate()` clamping and `clone()`.
- `config/store.zig`'s `ProfileStore` is the only writer of the running profile. It holds `live`, what the app shows including unsaved dialog edits, and `saved`, what's on disk. Runtime changes (thumbnail drags, tray toggles, History Panel toggles and position, assign-key membership) go through `update`/`setCharacterPosition`/`toggleGroupMember`, which apply them to both copies and save `saved`, so a dialog preview never reaches disk and closing the dialog unsaved (`discard`, a clone of `saved`) never undoes them. Painter and the panels hold `*const Config`, so a direct write fails to compile.
- Numeric bounds live in each section's `ranges` table (`.field = .{ min, max }`), and fields where a saved 0 means "use the default" are listed in `zero_means_default`. Every type with bounds has the same one-line `validate()`, `ranges_mod.clamp(Self, self)`, which applies both and then validates every nested setting that has a `validate()` of its own, so parents never call their children's by hand (only lists, like `Config.characters`, are looped explicitly). `config/ranges.zig` also serializes the bounds for the config dialog's input min/max (`buildValidationRangesJson`): profile sections under their config path, and list items and per-type settings under a kind key (`characters.opacity`, `notificationType.duration_ms`, `oreTable.price`, `global.dialogScale`), which the dialog's rebuilt rows name in a `data-range` attribute. `clampValue` clamps a single incoming value by the same table.
- Defaults and bounds follow one style:
  - A default is a literal on its field. Code that needs it reads `(Section{}).field` rather than repeating the number.
  - A default gets a name only when two places must hold the same value by construction, e.g. `PROFILE_FORMAT_VERSION` (the `formatVersion` default and the value every save is stamped with). Values that merely happen to match, like the `"Segoe UI"` font defaults, stay separate literals.
  - A bound belongs to a kind of value, not a setting: settings of the same kind share one named bound in `ranges.zig` (`FONT_SIZE`, `OPACITY`, `PERCENT`, `TEXT_OFFSET`, `SCREEN_X`/`SCREEN_Y`, `MAX_WINDOW_WIDTH`/`MAX_WINDOW_HEIGHT`, `WINDOW_SECONDS`), or one file-local `UPPER_SNAKE = .{ min, max }` tuple when the kind is confined to one file. A bound that fits only one setting, like each distinct timing limit, stays a literal in its table.
- `config/preview.zig` applies the dialog's live-preview patches to `ProfileStore.live` (`apply`); closing the dialog unsaved calls `ProfileStore.discard`.
- `config/profiles.zig` owns every profile file operation: loading with fallbacks, saving, creating (an exclusive create, so a name can't be claimed twice), copying, moving to `profiles/backup/` and restoring from there. Names from the dialog go through `validateName`, so they can't reach outside `profiles/`.

## The configuration window (`dialog/`)

A [zig-webui](https://github.com/webui-dev/zig-webui) WebView2 window around the embedded `config_dialog.html/css/js`, hosted in the main app so it edits the same in-memory config the app runs on.

- **`dialog/host.zig`** - the window's lifecycle on the main thread: `open()` (or focus, if it's already open), `tick()` from `onTimerTick` to notice it closing, which calls `main.onDialogClosed` (discard unsaved edits, resume hotkeys). `showWv` waits for WebView2 to connect, so it runs on a short-lived thread instead of stalling thumbnails. Also DPI/scale handling (a subclassed `WndProc` for `WM_DPICHANGED`, and `WM_EXITSIZEMOVE` posted back to the main thread to save the position) and which profile the window edits, which is the running one unless the user picks another.
- **`dialog/rpc.zig`** - the window's one binding, `rpc(method, argsJson)`. Every `pub fn` in `dialog/api/*.zig` is a method taking an arena and optionally an args struct, parsed from the JSON with `std.json`; its return value is serialized as `{"ok":true,"data":...}`, and any error is logged once there and returned as `{"ok":false,"error":{"code","message"}}`. webui calls in on its own threads, so calls are forwarded to the main thread (`SendMessageTimeoutA` with `WM_DIALOG_RPC`) and only touch app state there - except `api/background.zig`'s (`runs_on_caller`): pickers, ESI prices, Ultra Potato and window scans, which touch no app state and would otherwise stall the thumbnails.
- **`dialog/api/`** - `session.zig` (load, save and preview the profile and global settings), `profiles.zig`, `app.zig` (window positions, open clients from `Scout`, region select, hotkey recording, the window's scale and always-on-top) and `background.zig`.
- **`dialog/events.zig`** - pushes app-side changes into the page as `window.onAppEvent(name, payload)`: `regionSelected`, `winKeyCaptured` (a bare Win press while recording a hotkey, see `keyboard_hook.zig`'s `armWinKeyCapture`), `groupMembersChanged` (an assign key saved new members, so the form reloads them before a Save can overwrite them) and `profileSwitched`, so previews always target the running profile.
- **`dialog/resources.zig`** - assembles the page from the embedded HTML, CSS, JS, fonts and language catalogs.
- **`dialog/tools/`** - `esi_prices.zig` (Jita ore prices from the public ESI API) and `ultra_potato.zig` (see below).

## Threading model

Six threads of the app's own, plus webui's while the configuration window is open:

1. **Main thread** - the Win32 message loop, all window procs, all `SetWinEventHook`/low-level keyboard/mouse hook callbacks (Win32 delivers these to the installing thread), and `onTimerTick` (see below).
2. **Chatlog worker thread** (`chatlog.zig`, opt-out via `useThreading: false`) - log file I/O and parsing, communicating through the three `EventQueue(T)` queues.
3. **TTS worker thread** (`notifications/tts.zig`) - a lazily-started, persistent STA-COM thread draining a mutex-guarded command queue, so `Speak()` never blocks the caller.
4. **Sound worker thread** (`notifications/sound.zig`) - same lazily-started, persistent, mutex-guarded-queue shape as the TTS worker, decoding and playing custom notification sound alerts (WAV/MP3 via Media Foundation, played via waveOut) so `playAlert()` never blocks the caller and overlapping alerts don't cut each other off.
5. **Update-check thread** - one-shot, detached, writes into a mutex-guarded global `UpdateStatus` that the tray menu reads.
6. **Clipboard-upload thread** (`hotkeys/paste_upload.zig`) - one-shot, detached, spawned when a URL hotkey with `uploadClipboard` set is pressed; POSTs the clipboard to the target URL, copies the resulting page's URL back to the clipboard, then opens it.
- **Configuration window** (`dialog/`) - webui runs the WebView2 window on its own thread and calls `rpc` on per-event threads, which forward to the main thread via `WM_DIALOG_RPC` unless the method touches no app state (see `dialog/rpc.zig`). A short-lived thread shows the window, since that waits for WebView2 to connect. The main thread never blocks on webui, so a call waiting on the main thread can't deadlock it.

Inter-module communication is predominantly **direct calls on shared global pointers**, not an event bus: the core instances are published through one optional global pointer each, owned by their module (`painter.g_painter_ptr`, `scout.g_scout_ptr`, `hotkeys.g_hotkey_manager_ptr`) and used by `main.zig` itself as well as by OS callbacks - which can't carry a `self` pointer through the Win32 callback ABI - so there is never a second copy to keep in sync. Other `main.zig` globals (`g_chatlog_monitor`, the activity trackers, ...) stay private to it. Circular imports are fine in Zig, so modules call each other directly rather than through function-pointer indirection. The closest thing to real message passing is the chatlog event queues (cross-thread) and Win32 messages themselves, used for same-process signaling (tray → main loop, configuration window → main thread) and cross-process IPC (a second invocation → the running instance).

## The tick

`main.zig`'s `onTimerTick()`, fired by `WM_TIMER` at `config.timer.scanIntervalMs`, is the one driver every subsystem update cascades from, in fixed order:

```
Scout.update()                    window discovery / lifecycle reconciliation
  -> Painter.update()             sync scan results into thumbnail state
  -> Painter.updateNotifications()
  -> ChatlogMonitor.update()      queue commands / drain result+notification queues
  -> CombatTracker/MiningTracker.refreshAll()
       -> throttled push into Painter (own update_interval_ms, independent of scan cadence)
```

The expensive full `EnumWindows` rescan is itself throttled to roughly every 20 ticks rather than running every tick.

## Other subsystems

- **`tray.zig`** - system tray icon, right-click menu (profiles, dragging/auto-minimize/visibility/suspend-hotkeys toggles, restore saved positions, Close All, update notice), opens the configuration window.
- **`notifications/tts.zig`** - Windows SAPI via late-bound `IDispatch::Invoke` on its own STA-COM thread; `speakAlert()` is the fire-and-forget public API.
- **`notifications/sound.zig`** - custom per-notification-type sound alerts: decodes WAV/MP3 via Media Foundation's `IMFSourceReader` (hand-written COM vtables, transcribed from mingw-w64's headers rather than Microsoft's alphabetized Learn docs) and plays the PCM via winmm `waveOut`; `playAlert()` is the fire-and-forget public API, queued to a worker thread that does the decoding and playback.
- **`update.zig`** - checks GitHub Releases via `std.http.Client` on a background thread; its `UpdateStatus` feeds both the tray menu and the configuration window's notice. Opens the release page in a browser.
- **`hotkeys/paste_upload.zig`** - a URL hotkey's optional clipboard-upload path: POSTs the clipboard as form data to the target URL via `std.http.Client`, relies on the client's default redirect handling to land on the created paste's page (the standard Post/Redirect/Get pattern), copies that page's URL back to the clipboard, then opens it in a browser.
- **`list_view.zig`** - the compact `ClientList` view mode: a single custom-drawn panel (badge/name/system/notification per row) as an alternative to per-window DWM thumbnails, calling `clients/activation.zig` and `input.zig` directly for row clicks.
- **`notifications/history_panel.zig`** - the History Panel: an always-available, resizable panel (`display.showNotifInfoPanel`/`notifInfoPanelWidth`/`notifInfoPanelHeight`, independent of `viewMode`), structurally a near-twin of `list_view.zig`: notification history (newest-first, click a row to jump to that character), each row colored by the notifying character's name color and that notification type's configured text color. History lives in `notifications/history.zig`'s fixed-capacity ring buffer, owned by `Painter` (`notification_history`, pushed from `notify`); the panel redraws when its `revision` changes. The window's lifecycle and visibility rules (create/destroy, auto-hide with no characters, the tray toggle's force-visible override) live in the same file's `HistoryPanel`, a single field on `Painter`.
- **`util/`** - small app-agnostic helpers shared across features: `color.zig` (color math - `hsvToRgb` and related - behind the auto-generated system/character name colors) `format.zig` (ISK abbreviation and thousands separators for the overlay's and list view's stat text), `http_client.zig` (the GET/POST wrapper `update.zig` and `dialog/tools/esi_prices.zig` share), and `strings.zig` (string-list lookup).
- **`log.zig`** - the app's own file logger: buffered, size-rotated (`eve-maj.log`/`.old`, 5MB cap), a `scoped(name)` factory, mutex-guarded so it's safe to call from the crash handler. `openDebugConsole()` is the debug-level console, including a ctrl handler that flushes buffered lines before the console's close kills the process.
- **`types.zig`** - shared enums with no owning struct (`BorderStyle`, `TextPosition`, `LayoutMode`, ...), imported by nearly every module.
- **`platform/virtual_keys.zig`** - VK constants plus the hotkey string parser/formatter, including the convention for encoding mouse-button chords into the same `u32` ID space as keyboard VKs.
- **`region_select.zig`** - the "New Thumbnail Region" / "Edit Region" overlay (drag a rectangle, then adjust its edges and confirm with Save/Cancel), shared by `RegionFit` layout mode and the not-logged-in Thumbnail Space: an interactive (non-click-through) layered window spanning the full virtual desktop, built on `platform/gdi_overlay.zig`'s DIB/`UpdateLayeredWindow` machinery but with a real `WndProc` (unlike the click-through ghost/hint overlays in `painter.zig`). It's agnostic to which rectangle it's filling in - `config_dialog.js` decides that by which fields it writes the result into, and passes the region to edit, whether to hide thumbnails, and the translated overlay text (the language files are the page's) in its `Request`. The result goes back to the window as a `regionSelected` event.
- **`dialog/tools/ultra_potato.zig`** - Ultra Potato Mode: scans `%LOCALAPPDATA%\CCP\EVE\*\settings*\` for EVE's own `core_public__.yaml`, then line-patches its heaviest graphics keys to `-300` (backing up each file once first) rather than doing a full YAML parse/re-serialize; only reachable from the configuration window.
