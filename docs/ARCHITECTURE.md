# Architecture

A map of how the ~27k lines of Zig in `src/` fit together. This covers module responsibilities, ownership, threading, and control flow - not configuration (see [CONFIGURATION.md](CONFIGURATION.md)) or the build (see [BUILDING.md](BUILDING.md)).

Line numbers are call-outs to orient you, not guarantees - they will drift as the code changes.

## One binary, one owner of the config

`build.zig` builds one executable, `eve-maj-preview.exe` (entry point `main.zig`): the thumbnail/hotkey/notification app, which also hosts the configuration window in-process (see [The configuration window](#the-configuration-window-dialog)). `zig build config` runs it with `--config`, which opens that window, or asks an already-running instance to via the `open_config` protocol command.

There is one in-memory model and one writer: `main.zig` owns the running profile (`g_store`, a `ProfileStore`) and the global settings (`g_global_settings`), and the configuration window edits those directly rather than its own copies on disk.

## Startup (`main.zig`)

`main()` → `mainImpl()` does, in order:

1. Install crash handling (`crash.zig`): vectored exception handler, unhandled exception filter and minidump support; `main.zig` keeps only the root `panic` declaration pointing at `crash.handlePanic`, which writes to `logs/eve-maj.log`.
2. Check for `--protocol <url>` **before** the single-instance check, so protocol commands work even when another instance is already running; `protocol.forwardToRunningInstance` hands it over - see [protocol.zig](#protocolzig-and-cross-process-control).
3. Acquire a named mutex (`Global\EVE-Maj-Preview-SingleInstance`) to enforce single instance.
4. Load `GlobalConfig`, then the per-profile `Config` (default or `--profile`/`-p`).
5. Auto-register the `evemajpreview://` protocol handler if configured (`protocol.ensureRegistered`).
6. Construct subsystems in dependency order: `Scout` → `Painter` → `ChatlogMonitor` → the activity trackers (`activity/runtime.zig`'s `Trackers.setup`, which wires them into the monitor) → **then** start the chatlog worker thread, only once the trackers exist for it to feed. `reloadWithProfile` follows the same order, so a kept monitor's worker stays paused until the new trackers are wired in.
7. Register the hidden timer window (`WndProc` = `timerWindowProc`), `TrayIcon`, and a detached background thread for `UpdateChecker`.
8. Initial window scan and thumbnail creation, `HotkeyManager` setup, `SetTimer` at `config.timer.scanIntervalMs`, or once a second with no window tracked.
9. Enter the classic `GetMessageA`/`TranslateMessage`/`DispatchMessageA` loop.

`timerWindowProc` is the app's central message dispatcher: tray clicks, `WM_TIMER` (→ `onTimerTick`, see below), `WM_HOTKEY`, profile switches, incoming `WM_COPYDATA` from a second CLI invocation, and the configuration window's commands (`WM_KNOTS_COMMAND`).

## The central state owner: `Painter`

`thumbnail/state.zig` is not an app-state struct - it's ~70 lines defining two enums (`VisibilityState`, `ThumbnailState`) plus the legal-transition helpers (`transitionVisibility`/`tryTransitionVisibility`) that enforce them for `VisibilityState`; `ThumbnailState` is a plain style-lookup key with no transition logic of its own (see `ThumbnailWindow.effectiveRenderState` below). Code that acts on EVE's own client windows (not thumbnails) lives in `clients/`: `actions.zig` has the stateless actions (`minimizeAllClients`, `closeAllClients`, `moveAllClientsToSavedPositions`, `moveClientToPosition`), `auto_minimize.zig`'s `AutoMinimizer` minimizes idle clients (tracking each monitor's last-focused client so one can be spared), and `auto_move.zig`'s `AutoMoveVerifier` moves clients to saved window positions and re-checks them while EVE may still be repositioning its window. Painter holds one of each and calls them from `update()`.

The actual central mutable-state owner is **`Painter`** (`painter.zig`, ~800 lines): the thumbnail manager. It owns the set of `ThumbnailWindow`s and their state, keeps them in sync with what Scout finds, and schedules layout and redraws, delegating the work itself to the modules below. It owns:

- The thumbnail collection: `thumbnails: ArrayList(ThumbnailWindow)`, searched linearly since there are only ever a few dozen.
- The full thumbnail lifecycle: `createThumbnail`, `destroyThumbnail`, `cleanupClosedThumbnails`; the windows themselves are made and destroyed by `thumbnail/window.zig`. New thumbnails come from one path, `addMissingThumbnails`: per tick for newly found windows, and via `populate` at startup and after a profile reload. The options differ only where intended: auto-move follows `moveOnStartup` at startup, `autoMovePosition.enabled` for later arrivals, and never on reload, while a reload seeds system names from a `SystemNameSnapshot`. Every path reflows under one rule (`thumbnail/arrange.zig`'s `hasCountDependentLayout`), since `createThumbnail` sizes each cell against the count so far.
- Per-tick reconciliation of scan results into thumbnail state: `update()`, with logins and logouts handled by `onLogin`/`onLogout`.
- Notifications, as `notify` (one client), `notifyAll` (every client, for global user actions) and `updateNotifications`, implemented in `notifications/dispatch.zig`, which decides whether a notification shows (enabled, muted, suppressed, throttled) and triggers its sound and speech. Whether a notification feeds the "cycle to recently notified" queue follows from its type (`notification.isUserAction`), not the caller. Both take a `notifications/notification.zig` `Notification` payload (type plus optional `state`/`source`/`target`), which dispatch turns into display text with `notification.text`: the type's `custom_text`/`custom_text_alt` with `{name}` placeholders filled by the pure `notifications/template.zig` (each type's names come from `notification.placeholders`, which the config dialog offers as chips), falling back to `notification.defaultText`. Speech and sound go through `notifications/alert_effects.zig`, so nothing here touches `tts`/`sound` directly. The chatlog worker thread queues the payload, not text, so rendering happens on the main thread. Each thumbnail's on-screen notifications live in a `notifications/stack.zig` `NotificationStack` (newest first, bump-to-top per type, plus per-type throttle timestamps); the cycle-to-notified hotkey reads Painter's `notifications/notified_queue.zig` `NotifiedQueue`.
- Nothing for Travel Mode itself: left-behind detection is `travel/left_behind.zig`'s `check(painter, now)`, called on a throttled ~2s cadence from `onTimerTick`. Each thumbnail carries a travel-owned `LeftBehindState` (`travel`); Painter only calls `recordJump()` on it when a jump lands, and `check` reads it and raises alerts via `notify`. Compares each `ThumbnailWindow.system_name` (not jump-timestamp order) to find the group's current system, so a straggler who catches up is never mistakenly flagged just because their jump landed last - see [CONFIGURATION.md](CONFIGURATION.md#travel-mode).
- Deciding when to redraw: `renderThumbnail` diffs the thumbnail's cached `RenderSettings` to skip redundant redraws, then hands off to `thumbnail/overlay.zig` (see below).
- Applying layout to windows (`repositionAllThumbnails`, `resizeThumbnailIfNeeded`, `refreshAllThumbnailVisuals`, implemented in `thumbnail/arrange.zig`; `saveThumbnailPosition`). The math lives in `layout/`: `spaces.zig` decides which thumbnail space each character goes to (none in `Manual` placement mode, since `listed` returns no spaces; otherwise `spaceFor`: first active space holding one of its hotkey groups, else the active Unassigned Characters space, else the first space taking unassigned characters; a login-screen placeholder goes to the active Login Screen space, else the first space taking them) and its cell there (`assign`), with no I/O; `placement.zig` has the grid math plus a `Layout` view (config + thumbnail list, via `Painter.layout()`) for each space's grid (`spaceCells`) and hand-placed positions and sizes; `monitors.zig` has monitor bounds and DPI lookups.
- DPS/mining/bounty/resource values feeding into the overlay, kept in each thumbnail's `stats` (`thumbnail/window.zig`'s `ActivityStats`).
- Transient overlays: a `drag/overlays.zig` `GhostOverlay` (field `ghost_overlay`) outlining other saved positions while dragging, and a `platform/gdi_overlay.zig` `HintBox` (field `hint_box`) - a generic centered two-line box that dragging (`drag/overlays.zig`'s `showDragHint`) and region select (`dialog/api/app.zig`'s `startRegionSelect`) fill with their own text. Each overlay registers its own window class on first use. Fonts for both come from `FontCache.characterNameFont`. The hover zoom (`thumbnail/hover_zoom.zig`'s `HoverZoom`, field `hover_zoom`) is a click-through window pair made from the thumbnail window classes: its own DWM thumbnail of the hovered client, placed by `layout/zoom.zig`, under the thumbnail's overlay redrawn at the zoom's size into its own `RenderCache` through `overlay.renderOverlay` (Painter.renderThumbnail redraws it whenever the zoomed thumbnail's overlay changes). The module owns when it opens and closes: `onHover`, from `thumbnail/input.zig`'s mouse moves, and `check` (aliased as `Painter.checkHoverZoom`), run on mouse leave and every tick, since a hidden or moved thumbnail sends no leave. Whatever raises thumbnails batches `deferRaise` last, so the zoom stays on top.

Feature state that lives on each `ThumbnailWindow` is owned by its feature's module, not Painter: `render_cache` (`thumbnail/overlay.zig`), `notifications` (`notifications/stack.zig`), `auto_minimize` (`clients/auto_minimize.zig`, refreshed by `AutoMinimizer.check` itself), and `travel` (`travel/left_behind.zig`).

Each tracked character is a `ThumbnailWindow` (`thumbnail/window.zig`): `hwnd`/`text_hwnd`/`thumbnail_id`, `source_hwnd`, cached display strings/colors, `visibility_state`, and the `render_cache` (`thumbnail/overlay.zig`'s `RenderCache`) used for render skipping. Its render state (Active/Inactive/Alert/Minimized/Dragging) isn't stored - `effectiveRenderState()` derives it live on each render from focus (`Painter.active_source_hwnd`), `isWindowIconic`, active notifications, and drag state. In `ClientList`/`Nothing` view modes, `hwnd`/`text_hwnd` are sentinel values rather than real windows - see [thumbnail/list_view.zig](#other-subsystems).

## Window discovery → rendering pipeline

**`clients/scout.zig`**'s `Scout` owns discovery. `scanForEveWindows()` drives `EnumWindows`, matching each window against `config.windowFilters` by class name first (cheap pre-filter), then by executable path, which is only looked up for a new window that passes the class check (tracked windows are skipped before either); `findMatchingFilter` is the one matcher used for both new windows and re-checking tracked ones after a config reload. `trinityWindow`-class windows get a character name parsed from the title; other filters use their configured `name`. New windows are found only by the once-a-second rescan (a creation hook would wake the app for every window on the desktop, and EVE's is still hidden when created); between rescans, `EVENT_OBJECT_NAMECHANGE`/`DESTROY` `SetWinEventHook`s per tracked process, hooked when its first window is tracked and unhooked once none is left, catch renames and closes without other apps' events ever waking the main thread; `Scout.update()` reconciles these with the periodic full rescan.

Rendering is split four ways:

- **`platform/win32.zig`** - Win32 constants, `extern` declarations (including the `DwmRegisterThumbnail`/`DwmUpdateThumbnailProperties` family), struct layouts, plus small helpers built directly on those bindings with no app-specific knowledge (window title/class/exe-path lookups, window identity checks like `isOwnProcessWindow`/`isExplorerOwned`/`isDesktopShellWindow`, `setClickThroughStyle`, `shellOpen`, the COM `showFolderPicker`). No EVE- or config-aware logic.
- **`painter.zig`** and **`thumbnail/window.zig`** - the DWM integration and orchestration (above). `window.create()` creates a borderless layered popup window, calls `DwmRegisterThumbnail` to bind the EVE client's live DWM thumbnail into it, then creates a *second* layered window stacked on top for GDI-drawn overlay content (border, text, notifications). Each visible thumbnail is therefore two HWNDs, not one.
- **`thumbnail/`** - the overlay drawn into that second window. `overlay.zig` builds `RenderSettings` from config and thumbnail state (`createRenderSettings`), compares every field of them (walked at comptime, so new fields are included) for the redraw skip, and paints them (`renderThumbnailOverlay`, one `Layout` builder function per element); `draw.zig` holds the pixel/text primitives it and Painter's drag hint/ghost overlays share (`drawBorder`, `drawExclusionOverlay`, `measureText`, `renderText`, ...); `font_cache.zig`'s `FontCache` (owned by Painter, passed in) caches GDI fonts per (slot, DPI).
- **`platform/gdi_overlay.zig`** - the shared GDI leaf module: `OverlayBitmap` (a top-down DIBSection selected into a memory DC), alpha-fixup helpers for GDI text output, pixel-buffer `fillRect`, buffer-truncating `toBufZ`/`measureTextWidth`/`truncateTextToFit`, `registerWindowClass` (the common `WNDCLASSEXA` registration boilerplate), plus `HintBox`, the generic centered two-line hint window. It depends on nothing app-specific, and everything that draws with GDI uses it: `thumbnail/`, the panels, the drag overlays and `dialog/tools/region_select.zig`.
- **`platform/fonts.zig`** - embeds the bundled Cascadia Code/Mono TTFs and registers them process-privately (`AddFontMemResourceEx`) at startup, so GDI font lookups work on installs without Cascadia.

## Log monitoring and activity tracking

**`chatlog.zig`**'s `ChatlogMonitor` does all log I/O on a dedicated worker thread (`workerMain` → `processCommands`/`pollLogFiles`/`rescanForNewLogs`), decoupled from the main thread by four mutex-guarded `chatlog/queue.zig` `Queue(T)`s - `commands` (main → worker) and `system_updates`/`notifications`/`session_starts` (worker → main). `session_starts` carries each followed gamelog's session start, read from its file name, which `Scout.backdateLogin` uses to correct the login time of a character already logged in when the app started; that time drives the Session Timer overlay. The main-thread side, `ChatlogMonitor.update()`, only sends add/remove-character commands and delivers what the worker queued - the only point where its output touches `Painter`/`Scout`. Each field is owned by one thread: `requested` by the main thread, and the followed files, `wanted` characters and rescan state by the worker, which the main thread only touches once it's stopped. Each character's EVE character ID, learned from log file names, lives in `chatlog/character_ids.zig`'s `CharacterIds` (saved to `character_ids.json`), which both threads use and which locks its own map; the worker also reads the global settings' ore prices, which is why new global settings are only taken in while the worker is stopped (see `main.restartSubsystems`). Which gamelog lines become notifications is decided by `notifications/gamelog_events.zig`'s `classify()`, a pure line → `Notification` mapping called from the worker. Before that, `chatlog/lines.zig` reads each line with no I/O: whether it moves the character (a Local change, `(None) Jumping from`, `(None) Undocking from … to <system> solar system.`, or a conduit), and which activity handler it goes to; it also parses log file names and headers and joins lines split across reads (`LineAssembler`). `chatlog/utf16.zig` decodes the UTF-16 chatlogs, only ever whole characters. Each followed file is a `chatlog/tail.zig` `LogFile`: its handle stays open between polls, it reads what was appended (catching up in one poll, within a cap), backs off while idle, and scans back for the starting system when first opened. `chatlog/discovery.zig`'s `LogFinder` owns the log folders and their change watchers, and finds a character's newest log: by cached ID with the search filtered by Windows (`*_<id>.txt`), else by reading the `Listener:` header of only the newest 64 files, since a Chatlogs folder can hold tens of thousands. Both have unit tests (`zig build test`).

**`activity/tracker.zig`** is the DPS/mining-rate math, fed by log lines parsed on the chatlog worker thread. `CombatWindow`/`MiningWindow`/`BountyWindow` each wrap a `Ring(Event)`, a fixed-capacity ring buffer (no heap allocation after init) whose rates are the window total over the window, warming up from the first event of a streak; the windows add only their own alerts and rate splits. `CombatTracker`/`MiningTracker`/`BountyTracker` are one generic `Tracker(Window)` holding a window per character, and are explicitly cross-thread: the chatlog worker calls `addEntry`/`removeCharacter` while the main thread reads rates and checks alerts through `query`, which runs a window method under the tracker's own mutex.

**`activity/resources.zig`**'s `ResourceTracker` is unrelated to the chatlog pipeline above - it samples per-process CPU%/RAM/VRAM directly from the OS (`GetProcessTimes`, `GetProcessMemoryInfo`, and a PDH "GPU Process Memory" query for VRAM), keyed by `scout.EveWindow.process_id`. Main-thread only, no locking: `Trackers.tick` calls `sampleAll` on its own throttled interval (`config.resources.update_interval_ms`) and pushes the result into `Painter.updateResourceStatsForCharacter`, the same push-then-`renderDirtyThumbnails(null)` shape combat/mining/bounty use, just without their cross-thread queue.

**`activity/runtime.zig`**'s `Trackers` owns the live tracker instances for the current profile: `setup` matches them to the config while the chatlog worker is stopped (at startup and on every Save or profile switch), keeping each tracker that stays enabled with its history and new window length, freeing disabled ones and creating newly enabled ones, then wires them into the chatlog monitor, and `tick` pushes each tracker's values into Painter at its configured interval. The resource tracker alone follows the live config in `tick`, so its toggle previews before Save; the chatlog-fed trackers change only on Save, since the worker must be stopped first. See [CONFIGURATION.md](CONFIGURATION.md#resource-usage-overlay).

## Input & control surfaces

- **`hotkeys/`** - global hotkeys, split by concern:
  - `manager.zig` - `HotkeyManager` owns a single `hotkey_map: AutoHashMap(c_int, HotkeyAction)`, registration, suspend/dialog-pause, and `runAction()`, the one switch on the `HotkeyAction` union, which delegates to the modules below. Hotkey presses reach it through `handleHotkeyPress()`, which first gates on suspend/focus-requirement state; protocol URLs and the tray menu reach it ungated through `runGlobalAction()`.
  - `bindings.zig` - `HotkeyAction`, the ID bands (cycle-groups, global actions, per-character, profile-switch, app, URL) that let a single `WM_HOTKEY` ID reverse-map to an action (a global action's ID is the band base plus its `HotkeyAction` tag), and `GLOBAL_BINDINGS`, the table of global actions (config field, description, matching `protocol.GlobalAction`) that registration iterates and protocol requests are mapped through.
  - `cycling.zig` - every cycle (group, per-character, excluded, notified, all-clients, not-logged-in), all walking indices via one `CycleOrder` iterator, plus `CycleState`, the cursors not kept in config or `hotkey_map`, and the focus sync that moves them onto a manually focused client.
  - `exclusions.zig` - `Exclusions`, the characters excluded from cycling, by name in the order they were excluded. One instance lives for the whole app (not saved, kept across Save and profile switch); the manager holds a pointer, and Painter and travel read it through `isExcluded`.
  - `membership.zig` - the exclusion toggle shared by shift-click and the ToggleExclusion hotkey (refused for login-screen clients), clearing a logged-out character's exclusion, and the assign-hovered-thumbnail-to-group action.
  - `profile_switch.zig` - next/previous/specific profile hotkeys, handed to the main window as an async `WM_SWITCH_PROFILE`.
  - `launch.zig` - app, URL and return-to-last-app hotkeys.
  - `hook_bindings.zig` - `HookBindings`, the combo → hotkey-ID map (a binding's alternate combos all map to its one ID), hook install/uninstall and "exact combo, else bare key" `WM_HOTKEY` dispatch that both low-level hooks share.
  - `keyboard_hook.zig`, `mouse_hook.zig` and `paste_upload.zig`, below.
- **`hotkeys/keyboard_hook.zig`** - a `WH_KEYBOARD_LL` hook matching keyboard chords (including bare-modifier triggers like plain "Shift", which a keyboard-API-based approach can't represent) against bound combos and re-posting matches as synthetic `WM_HOTKEY` messages; also swallows a hotkey's key-up after a successful action changes focus (unconditionally for the Win key, since Windows treats an unmatched key-up as a Start Menu press regardless of focus) so the newly-focused window doesn't see a phantom key-up. `armWinKeyCapture()`/`disarmWinKeyCapture()` additionally keep the hook alive and swallow Win down/up unconditionally while the config dialog is recording a new binding (which otherwise unregisters everything), reporting the capture to the dialog since a swallowed key never reaches its own DOM listeners.
- **`hotkeys/mouse_hook.zig`** - a `WH_MOUSE_LL` hook mapping mouse-button chords to hotkey IDs and re-posting them as synthetic `WM_HOTKEY` messages, mirroring `keyboard_hook.zig`'s shape so `HotkeyManager` doesn't need a separate input path for mouse buttons.
- **`thumbnail/input.zig`** - the thumbnail/text-window `WndProc`s, which share one handler for the messages both windows treat alike: left-click routing (plain clicks to `clients/activation.zig`, shift-clicks to `hotkeys/membership.zig`'s exclusion toggle, on mouse-down or mouse-up per `clickTrigger`), the hover cursor and hover zoom, and right-button drags, handed to `drag/thumbnail.zig` (single-thumbnail drag with snapping, or a Ctrl group move batched through `DeferWindowPos`). Snapping itself (screen edges, other thumbnails, ghost positions) is `drag/snapping.zig`'s `applySnapping`, shared with `drag/panel.zig`, whose `handleMessage`/`beginPanelDrag` drive the list view's and History Panel's header drags.
- **`clients/animation.zig`** - `showClient()`, through which every minimize and restore of a client goes, so the No Animation setting covers them all.
- **`clients/activation.zig`** - `activate()`, where every thumbnail click, cycle hotkey and protocol switch ends: restore (through `clients/animation.zig`), foreground, reconcile thumbnail states, dismiss click-suppressible notifications, and sync hotkey cycle positions.
- **`platform/focus_grant.zig`** - the "focus grant" workaround for `SetForegroundWindow` silently refusing to switch focus unless the caller "just received user input" (true for a real click on our own window, not for a hotkey-triggered or auto-minimize-triggered refocus): a permanently-registered, physically unreachable `RegisterHotKey` binding (unused vk, every modifier combo) stays alive purely to borrow its foreground-lock exemption on demand - `forceSetForegroundWindow()` injects a synthetic keypress matching that binding, and the resulting genuine `WM_HOTKEY` (handled first in `timerWindowProc` via `handleWmHotkey()`, ahead of `HotkeyManager`'s dispatch) does the actual `SetForegroundWindow` call.
- **`protocol.zig` and cross-process control** - parses `evemajpreview://action/params` URLs, handles registry registration, and implements the IPC transport a second invocation uses to reach the running instance (`sendCommandToInstance`, which sends every `WM_COPYDATA` command through one `sendCopyData`, the receiving `copyDataBytes`, and `findExistingInstance`): character and profile switches, global hotkey actions, and `--config`'s `open_config`.

**Call chain, hotkey press → character switch:**
`WM_HOTKEY` → `timerWindowProc` → `HotkeyManager.handleHotkeyPress` → an action handler (`cycling.zig`'s `cycleGroup`, `activatePerCharacterGroup`, `cycleExcluded`, `cycleNotified`, ...) → `Scout.getHwndByName` → `activation.activate` → `focus_grant.forceSetForegroundWindow`.

**Call chain, protocol URL → character switch:**
second process invocation with `--protocol "evemajpreview://switch/Name"` → `protocol.parseUrl` + `findExistingInstance` + `sendCommandToInstance` → running instance's `timerWindowProc` receives `WM_COPYDATA` → `Scout.getHwndByName` → `activation.activate` (same tail as above).

## `config.zig`

Not just JSON schema - it's the shared model layer with both a wire format and runtime logic. `config.zig` holds `Config` itself (wire hooks, validation, per-character lookups, the runtime save calls) and re-exports everything else, so callers only ever import `config.zig`. The sections live in `src/config/`:

- `thumbnail.zig`, `display.zig`, `behavior.zig` (timer, snapping, interaction, auto-minimize, auto-move, exclusion, close-all), `activity.zig` (combat/mining/bounty/resources overlays, travel), `notifications.zig`, `chatlog.zig`, `characters.zig`, `system_colors.zig`, `hotkeys.zig` (global actions and cycling groups), `window_filters.zig` - one file per settings area.
- `global.zig` - `GlobalConfig` and the cross-profile hotkey bindings and ore price table it owns.
- Every type that holds saved settings is named `XxxConfig` (`ThumbnailConfig`, `SystemColorConfig`, `HotkeyGroupConfig`, `GlobalConfig`, ...); plain values (`Position`, `Argb`, `KeyList`, `OreEntry`) aren't.
- `files.zig` - the process-wide `std.Io`/environment handles (`setIo`, `setEnvironMap`), file names and size limit, `migrateLegacyLayout` (creates `data/` and `logs/` at startup and moves files older versions kept beside the exe into them), `atomicWriteFile`, `%VAR%` expansion.
- `profiles.zig` - profile files on disk (see below).
- `chatlog.zig`'s `ChatlogConfig.fromWire` also fills empty log folders with EVE's defaults under the shell's Documents folder.
- `auto_colors.zig` - `AutoColorStore`, owned by Painter rather than `Config`: resolves system/character name and border colours (overrides first, then the unique generated colour), kept in `data/colors.json` rather than the profile and loaded on first use.

What the layer does:

- Each settings section (`ThumbnailConfig`, `DisplayConfig`, `CharacterConfig`, ...) is declared once as its runtime struct; a section only declares `pub const Wire = wire.Wire(Self)`, and `config/wire.zig` generates that JSON shape plus saving, loading, freeing and cloning from its fields. `wire.encode`/`decode`/`free` (and the `*List` variants) work on any config type, using a type's own `toWire`/`fromWire`/`deinit` where it declares one (e.g. `ChatlogConfig`'s env-var expansion). Naming conventions pick the on-disk encoding: a `u32` named `*Color` is saved as a hex colour string, a `KeyList` (`config/key_list.zig`, every field named `hotkey*`/`*Key`) as one hex key code, or an array of them when it holds several; `std.ArrayList` fields are saved as arrays, and fields named in `runtime_fields` (allocators, Config's profile name, list items' ids) aren't saved. A default a runtime field can't hold, like `Config.windowFilters`' EVE filter, goes in `wire_defaults`. `Config` and `GlobalConfig` are generated the same way; `Config.fromWire` adds only the DPI migration, the always-present Login Screen and Unassigned Characters spaces (`config/spaces.zig`'s `ensureSpecialSpaces`) and resetting the `app`/`formatVersion` stamp, and `fromWire(.{})` is the default profile. Schema changes that move settings between sections are upgraded on the JSON tree before parsing instead (`config/migrate.zig`, through `wire.parseMigrated`), so the profile importer sees them too; v3 turned the old fit region and not-logged-in space into `thumbnailSpaces`, and a profile with an enabled space but no `display.placementMode` gets `ThumbnailSpaces`. `wire.toJsonAlloc`/`logJson` serialize and log either one the same way. `wire.parse` loads every settings file leniently: before converting the JSON, `config/readable.zig` walks the target type alongside it and drops each field, list item or map entry that doesn't fit (a type with its own parser declares `MapValue` to be walked into), so one bad hand-edited value only resets that setting. Only a file that isn't JSON fails; `config/profiles.zig` then copies it into `profiles/backup/` before running on defaults. The dialog's edits (`config/patch.zig`) parse strictly instead, so a bad value is rejected rather than defaulted.
- Two independent settings layers: `GlobalConfig` (`profiles/global.settings.json` - last-used profile, cross-profile hotkeys, log level) and per-profile `Config` (`profiles/<name>.json`).
- `Config` itself is plain data with read-only helpers: per-character overrides (`getCharacterSize`, `isExcludedFromMinimize`, ...), `validate()` clamping and `clone()`.
- `config/store.zig`'s `ProfileStore` is the only writer of the running profile. It holds `live`, what the app shows including unsaved dialog edits, and `saved`, what's on disk. Runtime changes (thumbnail drags, tray toggles, History Panel toggles and position, assign-key membership) go through `update`/`setCharacterPositions`/`setWindowPosition`/`toggleGroupMember`, which apply them to both copies and save `saved`; the configuration window edits `live` itself, so it shows them at once. A dialog preview therefore never reaches disk, and neither Save (`commit`, a clone of `live`) nor closing unsaved (`discard`, a clone of `saved`) undoes a runtime change. Painter and the panels read `live`; the parts set up once from the profile (Scout's window filters, the hotkey bindings, the chatlog monitor and trackers, the timer) read `saved`, and are rebuilt after a Save (`main.applySavedSettings`). The hotkey manager reads its bindings, and the groups and characters their ids index into, from `saved` (`config`), and every other setting from `live` (`live()`). The painter isn't rebuilt on a Save, since the dialog already previewed what was saved and a rebuild would flash every window; only a profile switch replaces it. The few settings it only reads when built are applied live instead: a view mode change rebuilds it (`main.onLiveProfileEdited`), the History Panel's on/off and both panels' configured positions are synced (`Painter.syncPanels`; a panel only moves when its configured position changes, so a drag with "remember position" off isn't undone), and windows that new window filters drop are reported closed by Scout. Painter and the panels hold `*const Config`, so a direct write fails to compile.
- `config/patch.zig` is the edit language an import is applied in: `set`, `insert`, `remove` and `move` ops addressed by a path of field names, where an item of a keyed list (`characters`, `hotkeyGroups`, `thumbnailSpaces`) is named by its runtime `id` rather than its position, so an edit still lands on the right item after others were added, removed or reordered. Values parse through the same wire format as the files. `write`/`writeAt` give a document, or the value at a path, in that shape (the saved JSON plus each keyed item's `id`). `assignIds` gives every keyed item an id, which the configuration window also tracks characters and groups by.
- Numeric bounds live in each section's `ranges` table (`.field = .{ min, max }`), and fields where a saved 0 means "use the default" are listed in `zero_means_default`. Every type with bounds has the same one-line `validate()`, `ranges_mod.clamp(Self, self)`, which applies both and then validates every nested setting that has a `validate()` of its own, so parents never call their children's by hand (only lists, like `Config.characters`, are looped explicitly). `clampValue` clamps a single incoming value by the same table.
- Defaults and bounds follow one style:
  - A default is a literal on its field. Code that needs it reads `(Section{}).field` rather than repeating the number.
  - A default gets a name only when two places must hold the same value by construction, e.g. `PROFILE_FORMAT_VERSION` (the `formatVersion` default and the value every save is stamped with). Values that merely happen to match, like the `"Segoe UI"` font defaults, stay separate literals.
  - A bound belongs to a kind of value, not a setting: settings of the same kind share one named bound in `ranges.zig` (`FONT_SIZE`, `OPACITY`, `PERCENT`, `TEXT_OFFSET`, `SCREEN_X`/`SCREEN_Y`, `MAX_WINDOW_WIDTH`/`MAX_WINDOW_HEIGHT`, `WINDOW_SECONDS`), or one file-local `UPPER_SNAKE = .{ min, max }` tuple when the kind is confined to one file. A bound that fits only one setting, like each distinct timing limit, stays a literal in its table.
- `config/profiles.zig` owns every profile file operation: loading with fallbacks, saving, creating (an exclusive create, so a name can't be claimed twice), copying, moving to `profiles/backup/` and restoring from there. Every name, from the dialog, a protocol link, `--profile` or `lastUsedProfile`, goes through `validateName`, so it can't reach outside `profiles/`; `load` falls back to the default profile on an invalid name and takes the file's spelling for one differing only in case.
- `config/import/` reads other preview tools' settings files and other EVE-Maj profiles. `importer.zig` recognises the format and lists the sections the file has (`analyze`), then turns the chosen ones into patch ops (`build`), which the configuration window applies to the profile it edits. Each format module (`eve_x.zig` for EVE-X and EVE-MultiPreview in both of EVE-X's layouts, `eve_apm.zig` for EVE-APM's QSettings INI, `eve_o.zig` for EVE-O) fills a `Draft` (`draft.zig`): a partial profile in its saved shape plus notes, as translation keys, on what was and wasn't brought in. `toOps` merges it into the profile being edited, matching characters and groups by name and dropping the empty placeholder the dialog seeds into an empty list. `own.zig` loads EVE-Maj profiles through the normal loader, so an older format migrates the same way, and offers every saved section. Positions from the other tools were saved DPI-unaware and are scaled on the way in; example entries from their default configs and window-title keys that aren't characters are skipped (`values.characterName`), and `own.zig` drops them from an EVE-Maj profile's characters too.

## The configuration window (`dialog/`)

Drawn with [knots](https://github.com/knots-ui/knots), an immediate-mode UI on Vulkan, in a window of its own on the main thread, so it edits the same in-memory config the app runs on. knots is vendored in `deps/knots/` with a few local patches (listed in its `PATCHES.md`, each marked `EVE-Maj patch`): a colour picker without hex or alpha, a popup that stays on screen, and boxes snapped to whole pixels. Every frame redraws the open tab from the settings, so there's no form state to keep in sync: a control reads its setting as it's drawn and writes it straight back.

- **`dialog/knots/host.zig`** - the window's lifecycle. `open()` (or focus, if it's already open) posts `open` to the timer window, which runs the window as a nested loop on the main thread until it closes, so the tick, hooks and tray keep running. A short-lived `WH_CBT` hook creates the window at its saved position. The host subclasses knots' window to ask before closing with unsaved changes, to remember where the window was left, and to give a recording hotkey field the keys it binds. Commands that replace the documents or touch the app (Save, Discard, profile actions, picker and price results) are posted back to the timer window as `WM_KNOTS_COMMAND`, so none runs inside a frame.
- **`dialog/knots/session.zig`** - what the window edits: the running profile's `live` copy (so edits preview on the thumbnails at once), or a draft when it edits another profile, and a draft of the global settings. Every change goes through `Ref.set` (or a list's `append`/`remove`/`move`), which copies strings, clamps the document and previews it; replaced strings are freed a frame later, since the frame being drawn may still show them. Whether each document is dirty is decided by comparing it with what's saved. Save commits the store (or writes the draft and switches to it) and has the restart that follows take the global draft. Until then the global draft stands in for the live global settings: `liveGlobal` returns it while the window is open (the hotkey manager's `liveGlobal()` reads it), and the log level follows it at once.
- **`dialog/knots/form.zig`** - the frame: header, sidebar (tab glyphs, and the open tab's sections to jump to), the open tab, the footer's search, status and Save, and the prompts. **`tabs/`** holds one file per sidebar tab.
- **`dialog/knots/widgets.zig`, `bind.zig`, `style.zig`** - sections (with their `?` field hints and the sidebar's section list), groups that dim while what they depend on is off, two-click confirm buttons, drag-to-reorder rows; controls bound to one setting each; and every style. A tab can turn on aligned rows (`widgets.useAlignedRows`): each row's label on the left and its control at the right edge, rows divided by a line, switches in place of checkboxes, and units inside their boxes. The Display tab (`tabs/display.zig`) uses them; its Thumbnail Placement section, the placement mode then either the hand-placement settings or a reorderable list of thumbnail spaces beside the selected one's details, is `tabs/placement.zig`; `tabs/hotkey_groups.zig` carries group renames and removals into the spaces, which hold groups by name.
- **`dialog/knots/hotkey.zig`** - the hotkey field. While it records, the host's window procedure hands it the key, mouse button and wheel messages it binds, and the live hotkeys are suspended so they don't fire; a bare Win press comes from `keyboard_hook.zig`'s `g_on_win_key`. It also finds which combos are bound more than once, for the conflict outline.
- **`dialog/knots/search.zig`** - the settings search: the first search draws every tab once out of sight, recording each section's text, then hides the sections and tabs that don't match.
- **`dialog/knots/import_dialog.zig`, `profiles.zig`, `header.zig`** - the profile dropdown and its actions, and importing (see `config/import/`) and restoring backups.
- **Others** - `region.zig` (drawing a thumbnail space's rectangle with `dialog/tools/region_select.zig`, targeting the space by id), `positions.zig` (saved window positions), `prices.zig` (Jita prices, fetched on a thread of their own), `pickers.zig` (folder and file pickers, likewise), `window_picker.zig` (the running-window list), `suggest.zig` (open clients' names under a name box), `glyphs.zig` (icons drawn as pixel bitmaps, since Geist lacks most of them and knots doesn't antialias lines), `images.zig` (bundled bitmaps), and `lang.zig` (labels from `lang/en.json`, e.g. each notification type's).
- **`dialog/tools/`** - `esi_prices.zig` (Jita ore prices from the public ESI API), `region_select.zig` and `ultra_potato.zig` (both below). **`dialog/run_on_startup.zig`** applies Run on Startup when it's saved.

## Threading model

Six threads of the app's own:

1. **Main thread** - the Win32 message loop, all window procs, all `SetWinEventHook`/low-level keyboard/mouse hook callbacks (Win32 delivers these to the installing thread), and `onTimerTick` (see below).
2. **Chatlog worker thread** (`chatlog.zig`) - log file I/O and parsing, communicating through the four `chatlog/queue.zig` queues.
3. **TTS worker thread** (`notifications/tts.zig`) - a lazily-started, persistent STA-COM thread draining a mutex-guarded command queue, so `Speak()` never blocks the caller. Its thread, queue and shutdown come from `notifications/worker.zig`'s `Worker`, shared with the sound worker.
4. **Sound worker thread** (`notifications/sound.zig`) - the same `Worker`, keeping Media Foundation started while it decodes and plays custom notification sound alerts (WAV/MP3 via Media Foundation, played via waveOut) so `playAlert()` never blocks the caller and overlapping alerts don't cut each other off.
5. **Update-check thread** - one-shot, detached, writes into a mutex-guarded global `UpdateStatus` that the tray menu reads.
6. **Clipboard-upload thread** (`hotkeys/paste_upload.zig`) - one-shot, detached, spawned when a URL hotkey with `uploadClipboard` set is pressed; POSTs the clipboard to the target URL, copies the resulting page's URL back to the clipboard, then opens it.
- **Configuration window** (`dialog/knots/`) - runs on the main thread as a nested loop; only its folder and file pickers and its ore price fetch get a short-lived thread each, which posts its result back as a `WM_KNOTS_COMMAND`.

Inter-module communication is predominantly **direct calls on shared global pointers**, not an event bus: the core instances are published through one optional global pointer each, owned by their module (`painter.g_painter_ptr`, `scout.g_scout_ptr`, `hotkeys.g_hotkey_manager_ptr`, `exclusions.g_exclusions_ptr`) and used by `main.zig` itself as well as by OS callbacks - which can't carry a `self` pointer through the Win32 callback ABI - so there is never a second copy to keep in sync. Other `main.zig` globals (`g_chatlog_monitor`, the activity trackers, ...) stay private to it. Circular imports are fine in Zig, so modules call each other directly rather than through function-pointer indirection. The closest thing to real message passing is the chatlog event queues (cross-thread) and Win32 messages themselves, used for same-process signaling (tray → main loop, configuration window → main thread) and cross-process IPC (a second invocation → the running instance).

## The tick

`main.zig`'s `onTimerTick()`, fired by `WM_TIMER` at `config.timer.scanIntervalMs` (once a second while no window is tracked and the configuration window is closed, via `tickIntervalFor`), is the one driver every subsystem update cascades from, in fixed order:

```
Scout.update()                    window discovery / lifecycle reconciliation
  -> Painter.update()             sync scan results into thumbnail state
  -> Painter.updateNotifications()
  -> ChatlogMonitor.update()      queue commands / drain result+notification queues
  -> CombatTracker/MiningTracker rates, computed per client
       -> throttled push into Painter (own update_interval_ms, independent of scan cadence)
       -> alert checks (Taking Damage, Laser idle, Mining stopped) once a second
```

The expensive full `EnumWindows` rescan is itself throttled to at least once a second rather than running every tick, whatever the scan interval: it runs on the last tick that keeps the gap within a second (`schedule.nextTickWouldBeLate`).

The throttled pushes, alert checks and travel check measure from the tick's start, not the time after its work, and run on the tick nearest their interval (`util/schedule.zig`'s `isDue`), so timer jitter can't skip a whole tick at long scan intervals.

## Other subsystems

- **`tray.zig`** - system tray icon, right-click menu (profiles, dragging/auto-minimize/Travel Mode/visibility/History Panel/suspend-hotkeys toggles, clear notification history, restore saved positions, Close All, update notice), opens the configuration window.
- **`notifications/tts.zig`** - Windows SAPI via late-bound `IDispatch::Invoke` on its own STA-COM thread; `speakAlert()` is the fire-and-forget public API.
- **`notifications/sound.zig`** - custom per-notification-type sound alerts: decodes WAV/MP3 via Media Foundation's `IMFSourceReader` (hand-written COM vtables, transcribed from mingw-w64's headers rather than Microsoft's alphabetized Learn docs) and plays the PCM via winmm `waveOut`; `playAlert()` is the fire-and-forget public API, queued to a worker thread that does the decoding and playback.
- **`update.zig`** - checks GitHub Releases via `std.http.Client` on a background thread; its `UpdateStatus` feeds both the tray menu and the configuration window's notice. Opens the release page in a browser.
- **`hotkeys/paste_upload.zig`** - a URL hotkey's optional clipboard-upload path: POSTs the clipboard as form data to the target URL via `std.http.Client`, relies on the client's default redirect handling to land on the created paste's page (the standard Post/Redirect/Get pattern), copies that page's URL back to the clipboard, then opens it in a browser.
- **`thumbnail/list_view.zig`** - the compact `ClientList` view mode: a single custom-drawn panel (badge/name/system/notification per row) as an alternative to per-window DWM thumbnails, calling `clients/activation.zig` and `thumbnail/input.zig` directly for row clicks.
- **`platform/panel_window.zig`** - `PanelWindow`, the layered panel both the list view and the History Panel draw into: its window, font, bitmap, resizing, presenting, and skipping a redraw when the frame's signature is unchanged.
- **`notifications/history_panel.zig`** - the History Panel: an always-available, resizable panel (`display.showNotifInfoPanel`/`notifInfoPanelWidth`/`notifInfoPanelHeight`, independent of `viewMode`), drawn into the same `PanelWindow` as the list view: notification history (newest-first, click a row to jump to that character), each row colored by the notifying character's name color and that notification type's configured text color. History lives in `notifications/history.zig`'s fixed-capacity ring buffer, owned by `Painter` (`notification_history`, pushed from `notify`); the panel redraws when its `revision` changes. The window's lifecycle and visibility rules (create/destroy, auto-hide with no characters, the tray toggle's force-visible override) live in the same file's `HistoryPanel`, a single field on `Painter`.
- **`util/`** - small app-agnostic helpers shared across features: `color.zig` (the auto-generated system/character colors: `AutoColors`, which keeps each name's color and evicts the least recently seen, and `pickDistinctColor`, which picks the palette color farthest in OKLab from those already taken; plus `withAlpha`, `lighten` and `inkFor`), `format.zig` (ISK abbreviation and thousands separators for the overlay's and list view's stat text), `http_client.zig` (the GET/POST wrapper `update.zig` and `dialog/tools/esi_prices.zig` share), `schedule.zig` (when work run from the timer tick is due), and `strings.zig` (string-list lookup).
- **`log.zig`** - the app's own file logger: buffered, size-rotated (`logs/eve-maj.log`/`.old`, alongside the crash minidump, 20MB cap; if the log can't be renamed it keeps appending and retries), appending at the file's real end each flush so a second instance's lines aren't overwritten, a `scoped(name)` factory, mutex-guarded so it's safe to call from the crash handler. `openDebugConsole()` is the debug-level console, including a ctrl handler that flushes buffered lines before the console's close kills the process; saving a log level opens it or hides it (`closeDebugConsole()`), hidden rather than freed since `std.debug.print` keeps the stderr handle it first printed through.
- **`config/types.zig`** - the enums settings fields are typed with (`BorderStyle`, `TextPosition`, `RegionFitDirection`, ...). `FontWeight` is defined in `platform/fonts.zig` instead, since `platform/` can't depend on `config/`, and re-exported here.
- **`platform/virtual_keys.zig`** - VK constants, and `KEY_NAMES`, the one table of every bindable key and its spelling, which both the hotkey formatter and parser read, and the config dialog's recorder spells keys with; plus the convention for encoding mouse-button chords into the same `u32` ID space as keyboard VKs.
- **`dialog/tools/region_select.zig`** - the "New Thumbnail Region" / "Edit Region" overlay (drag a rectangle, then adjust its edges and confirm with Save/Cancel), used for every thumbnail space: an interactive (non-click-through) layered window spanning the full virtual desktop, built on `platform/gdi_overlay.zig`'s DIB/`UpdateLayeredWindow` machinery but with a real `WndProc` (unlike the click-through ghost/hint overlays owned by Painter). It's agnostic to which rectangle it's filling in - `dialog/knots/region.zig` decides that, passes the region to edit, and gets the result through its `on_result` callback.
- **`dialog/tools/ultra_potato.zig`** - Ultra Potato Mode: scans `%LOCALAPPDATA%\CCP\EVE\*\settings*\` for EVE's own `core_public__.yaml`, then line-patches its heaviest graphics keys to `-300` (backing up each file once first) rather than doing a full YAML parse/re-serialize; only reachable from the configuration window.
